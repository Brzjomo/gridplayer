# 设计方案：同步偏移对齐（Sync Offset）

> 状态：**P1 已实现**（见 §11）。P3 及以后尚未开工。
> 分支：`feat/sync-offset`
> 目标场景：同一事件的多机位/多路录像，各自起始时间与时长不同，需要严格对齐后同步观看。
> 已定的取舍（见 §13）：不做持续校正；旧同步模式保留在菜单里；内部存毫秒、UI 另显示帧数；辅助手段优先做音频。

## 1. 问题

现有同步（`SeekSyncMode`，`params/static.py:200`）只有两种模式，且都是**被动镜像**：

| 现有模式 | 行为 | 为什么对本场景无用 |
| --- | --- | --- |
| `PERCENT` | 某个视频 seek 后，按**百分比**把位置推给其他视频 | 百分比假设所有视频起始点与时长一致。时长不同则同一百分比对应完全不同的真实时刻。 |
| `TIMECODE` | 某个视频 seek 后，按**绝对时间**把位置推给其他视频 | 假设所有视频的"文件第 0 秒"是同一个真实时刻。多机位录像的起始时间各不相同。 |

两者共同的根本缺陷：**没有"该视频的第 T 秒对应哪个真实时刻"这一信息**。它们只能让所有视频停在相同的时间刻度上，而不是相同的真实时刻上。

用户的实际需求（原文示例）：三个录像，视频1 在 `00:05` 时为真实时刻 7:00:00，视频2 在 `01:15` 时才是 7:00:00，视频3 在 `00:48`。同时播放时必须让三者都停在 7:00:00 那一帧。

## 2. 核心语义

给每个视频增加一个**同步点**（sync offset），定义为：

> `sync_offset_ms` = 该视频时间轴上，对应"公共参考时刻"的那一点。

不变量：对所有视频 i、j

```text
t_i - offset_i == t_j - offset_j        # 这个差值就是公共真实时钟
```

在上例中：`offset_1 = 5000`、`offset_2 = 75000`、`offset_3 = 48000`。

由此推出播放关系。令 master 为参考视频：

```text
t_i = t_master + (offset_i - offset_master)        # 记 delta_i = offset_i - offset_master
```

验证：master = 视频1 在 `t=5s` 时，视频2 = `5s + 70s = 75s` ✓，视频3 = `5s + 43s = 48s` ✓。

**为什么存绝对值而不是存 delta。** delta 依赖 master 的选择，换 master 就要重算全部数值，且存进播放列表后语义会随"哪个是 master"漂移。存绝对值则每个视频自洽，master 只是显示用的参照系，可以随时切换而不改数据。

**方向的措辞需要你确认**（见 §13 问题 1）。上面 `delta_i > 0` 表示"视频 i 必须比 master 播得更靠后（seek 更远）"。UI 上我会写成"偏移 +00:01:10.000（靠后）"以避免歧义。

## 3. 数据模型与持久化

### 3.1 新字段

`gridplayer/models/video.py`，`Video` 增加：

```python
# 该视频时间轴上对应公共参考时刻的那一点；None 表示未设置（等同 0）
sync_offset_ms: int | None = None
```

用 `int | None = None` 而不是 `int = 0`，原因：`Playlist.dumps()` 用 `model_dump(exclude_none=True)`（`models/playlist.py:356`），`None` 会自动省略，**未对齐的播放列表不会多出一堆 `"sync_offset_ms": 0` 噪音**，也不需要改写入器。非零值才落盘。

刻意**不**放进 `PlaylistVideoDefaults`，也**不**标 `session_field`：它是"这段素材的内容属性"，不是用户偏好。就像 `loop_start`/`current_position` 一样属于单个视频。

### 3.2 需要同步照顾的地方

| 位置 | 处理 |
| --- | --- |
| `Playlist._video_data` | 无需改动（`exclude_none` 已处理） |
| `VideoBlock.apply_snapshot` | 快照恢复时一并带入偏移 |
| `VideoBlock.set_video` | 换视频即换偏移，重置到新视频的值 |
| 拖放换位（`swap_video`/`layout_drop`） | 偏移跟着 `Video` 对象走，天然正确——**但需测试确认**，因为 `VideoBlocks.reindex` 会改索引 |
| 快照（`Snapshot`） | 快照自带的 `videos` 列表已含偏移，天然正确 |

### 3.3 新增设置

`settings.py` 的 `_default_settings`：

```python
"playlist/sync_offset_enforce": True,        # 播放期间持续校正
"playlist/sync_offset_drift_frames": 2,      # 漂移超过该帧数才重新 seek
"playlist/sync_offset_reference": "",        # 参考视频的 block id，空 = 第一格
```

并在 `params/defaults_fields.py` 的 `PLAYLIST_FIELDS` 加对应行（放进 "Playback" 段），`params/menu.py` 的 `Playlist Settings` 子菜单加菜单项。注意 `AGENTS.md` 的翻译上下文规则：同一开关在菜单和设置表单都出现时用**设置名作上下文**。

## 4. 播放期强制执行

这是与现有 `sync` 的本质区别：现有逻辑只在 seek 时触发一次，本功能需要**持续成立**。

### 4.1 两个触发源

| 触发 | 动作 |
| --- | --- |
| **权威变更**：seek、从暂停转播放、改变播放速率、载入完成、切换参考视频 | 以 master 的当前位置为基准，算出所有 `t_i`，逐个 `set_time` |
| **持续校正**：master 的 `time_changed` 信号（已有，`VideoBlock.time_change`） | 比较每个视频的实际位置与期望值，超阈值才纠正 |

### 4.2 漂移校正

```text
expected_i = t_master + delta_i
drift_i    = actual_i - expected_i
if abs(drift_i) > threshold_i:  seek_i(expected_i)
```

- `threshold_i` 按**该视频自己的帧时长**换算：`drift_frames × 1000/fps_i`，并设一个下限（约 40ms）避免 fps 很高时疯狂 seek。
- 校正**只对正在播放的视频**做；暂停中或已越界的视频跳过。
- `fps` 未知（`VideoTrack.fps is None`）时退回固定毫秒阈值。

**风险：过度校正比漂移更难看。** seek 在硬件模式要重设 native surface，代价高；在自适应流上还要走 `_follow_seek` 的重试逻辑（`video_block.py` 的 `SEEK_RETRIES`）。因此默认阈值要宽松（2 帧），且必须可调、可关闭。若实测抖动明显，退路是改为"只在暂停/手动 seek 时对齐 + 提供一个'立即重新对齐'动作"。

### 4.3 与现有 seek-sync 的关系

建议**新增** `SeekSyncMode.OFFSET`，而不是改 PERCENT/TIMECODE 的语义：

```python
class SeekSyncMode(AutoName):
    DISABLED = auto()
    PERCENT = auto()
    TIMECODE = auto()
    OFFSET = auto()      # 新增
```

这样旧播放列表里的 `seek_sync_mode` 值仍然可读、行为不变。是否**移除**旧的两项见 §13 问题 2。注意新增枚举值要同步 `_seek_sync_modes()`（`defaults_fields.py:91`）和 settings 的迁移逻辑——按 `settings.py:198` 的惯例，如果语义变了要加迁移。

## 5. 越界提示

对 master 在 `T`，视频 i 的期望位置 `t_i = T + delta_i`：

| 情况 | 行为 |
| --- | --- |
| `t_i < 0` | 位置钳到 `0`，**暂停**该视频，格内显示"视频尚未开始" + 差值 |
| `0 ≤ t_i < length_i` | 正常播放/定位；若此前越界则恢复播放 |
| `t_i ≥ length_i` | 钳到末尾，暂停，显示"视频已结束" + 超出量 |

用户原文要求显示"超出视频范围"以及"超出多少时间"。建议**区分"尚未开始"与"已经结束"**——两者对使用者的含义完全不同（前者等一会儿就有画面，后者永远不会有了）。两个文案都附上超出量：

```text
视频尚未开始（差 00:00:05.000 · 125 帧 @25fps）
视频已结束（超出 00:00:12.300）
```

实现落在**状态显示层**。`widgets/video_status.py` 已有 `VideoStatus`（loading/info 两种子状态），`VideoBlock.update_status(info_text, percent)` 已经存在，因此可以复用状态机制而不是新造浮层——新增一个"越界"状态类型，带标题 + 副标题（差值）。需注意 `_paint_stopped_chrome` 与 overlay 的 `is_overlay_fits` 逻辑，别让提示被 overlay 遮住。

## 7. 音频包络 / 频谱辅助

### 7.1 关键风险：amem 会夺走音频输出

这一点必须写在最前面，因为它决定了整个架构：

> `libvlc_audio_set_callbacks`（amem）安装回调后，VLC 不再把音频送给真实输出设备。

也就是说，**如果直接在正在播放的 player 上装回调，用户就听不到声音了**。对播放器来说这是不可接受的。

因此音频分析必须走**独立的分析 player**：

- 在解码子进程里额外创建一个 `vlc.MediaPlayer`，用**独立实例选项**（`--no-video`、静音）创建，与真实播放器互不干扰；
- 它自己 seek 到目标区间、自己解码、自己出包络，**不连接任何输出**；
- 真实播放器完全不动，声音照常。

由于 `ProcessManager._get_available_instance` 是按 **options 相等 + 人数未满** 复用实例的（`multiprocess/process_manager.py:168`），分析 player 选项一致，会自然聚到一个（或数个）分析实例上。但默认 `player/video_driver_players = 4` 会限制一个实例容纳的 player 数——9 格网格就需要多于 4 个分析 player。方案：给分析实例单独设一个更大的 `players_per_instance`（分析 player 很轻，只有音频解码）。

### 7.2 采集实现

新增 `gridplayer/vlc_player/audio_monitor.py`，结构对齐已有的 `image_decoder.py`（同一个作者、同一套 smem + 回调模式，可直接照抄骨架）：

```python
class AudioMonitor:
    def attach_media_player(self, media_player):
        media_player.audio_set_format_callbacks(self.format_cb, self.cleanup_cb)
        media_player.audio_set_callbacks(
            self.play_cb, self.pause_cb, self.resume_cb, self.flush_cb, self.drain_cb, None
        )
```

- **format 回调里主动降规格**：请求 `S16N`、**单声道**、**8000 Hz**。VLC 会替我们重采样，之后纯 Python 的处理量下降一个数量级（48kHz 立体声 → 8kHz 单声道，数据量降到 1/12）。这是**为了绕开 numpy 而必须做的事**。
- **play 回调**里对每个 block 算 RMS 包络（以及可选的频带能量），写入 `SafeSharedMemory`。
- **flush 回调**里重置采样计数器——seek 之后必须重新锚定，否则时间戳全错。
- **时间戳用采样计数**而不是 `get_time()`：`media_time = 起始时间 + 已交付采样数 / 采样率`。`get_time()` 在回调触发时本身有滞后，用它会把包络整体平移（各视频平移量还不一定相同）。采样计数是精确的。
- 传输量很小（包络按 20ms 一块 ≈ 50 包/秒），走已有的命令通道（`cmd_send`）即可，不必像视频帧那样开共享内存。

### 7.3 纯 Python DSP 的可行性

不用 numpy 的约束下，算力预算（单视频）：

| 方案 | 每秒操作量 | 纯 Python 可行性 |
| --- | --- | --- |
| RMS 包络 @8kHz，20ms 块 | 8000 次乘加 | ✅ 轻松（约 5–10ms CPU/秒） |
| 8 频带 Goertzel @8kHz，窗长 128 | 8×128×50 ≈ 51k | ✅ 可以（约 20–40ms CPU/秒） |
| 全谱 FFT @48kHz 立体声 | — | ❌ 必须上 numpy，而 numpy 会打死 32 位构建 |

结论：**降采样后做少量频带的 Goertzel**是可行的，能画出用户要的"频谱条"；全谱 FFT 不可行。好在对齐这件事，**包络的峰值（关门声、拍手、讲话起始）本身就是最好的锚点**，粗频谱主要是辅助确认。

### 7.4 两种取数策略

| 策略 | 优点 | 缺点 |
| --- | --- | --- |
| **按需片段**（推荐先做）：打开对话框时，对每个视频静默解码 `[T−5s, T+5s]` | 实现简单、CPU 只在需要时耗、无持续流式管道 | 移动位置后需要重新采样 |
| **实时滚动**：分析 player 常驻，持续推包络 | 拖时间轴时同步更新，体验更好 | 管道、内存环形缓冲、生命周期都更复杂 |

建议**先做按需片段**，验证对齐效果，再决定是否上实时滚动。

## 8. 自动对齐（互相关）

如果 §7 已经能拿到包络，那么**自动算偏移几乎是免费的**，而且比人工看频谱更省事：

```text
对每对视频，在重叠窗口内对两条包络做互相关，取峰值位置 → 最佳 delta
```

窗口取 10 秒、20ms 一块 = 500 个采样点，朴素的 O(n²) 互相关只有 25 万次操作，纯 Python 几毫秒就完了。完全不需要 FFT。

这可能是整个功能里**性价比最高的一环**：用户按一个按钮，三个视角自动对齐，频谱图退化为"验证 + 手动兜底"。

限制要说清楚：

- 只在**两段素材在窗口内确实有共同音频内容**时有效；
- 静音录像完全无效（见 §9）；
- 若两机位麦克风离得远、拾音内容差异大，相关性会很弱——需要给出置信度，弱相关时明确提示"未找到可靠匹配"，而不是硬给一个错的值。

## 9. 无音轨场景：缩略图胶片条　【已否决】

> **结论：不做。** 用户明确否决，理由是实际运用场景不合适——
> **三路画面几乎没有一致的内容**。
>
> 原本的设想是"多机位拍同一事件时，同一时刻的画面通常相似"。实际素材不是这样：
> 各机位朝向、焦距、遮挡都不同，同一时刻能看到的共同内容极少，
> 因此按画面找共同时刻不成立。
>
> 由此推出的结论（见 [roadmap.md](roadmap.md)）：**音频是唯一的自动对齐途径**。
> 自动对齐在某些素材上可能根本不成立，那时就诚实退回手动工具，
> 而不是再造一条同样不成立的自动路子。
>
> 保留下面原文，是为了记录这个判断曾经怎么下的、以及为什么被推翻。

"多个视角的录像"很可能是**安防/监控录像**，而监控录像**经常没有音轨**（或只有一路有）。那样频谱和互相关全都用不上。

替代方案是**视觉指纹**：把每个视频在 `[T−5s, T+5s]` 内每隔 0.5 秒抓一帧，缩成小图排成胶片条，人眼对齐。多机位拍同一事件时，同一时刻的画面通常相似，视觉对齐往往比听觉更直观。

好在**抓帧的基础设施已经存在**：`vlc_player/image_decoder.py` 已经在用 vmem 回调把帧写进共享内存，`VideoDriver.snapshot()` / `screenshot()` 也已经可用。用同一个独立分析 player（这次选项是 `--no-audio`）就能抓，架构与 §7 完全对称。

因此建议：**§7（音频）与 §9（视觉）作为并列的辅助手段，由用户按素材选择**，不要只押注音频。

**用户读到本节后否决了它**：实际素材里三路画面没有一致内容，这条并列手段不存在。

## 10. 已知局限（需要在 UI 上诚实说明）

1. **VLC 的 seek 精度不是帧精确的。** `set_time(ms)` 定位到关键帧附近再解码前进，实际落点与请求值可能有偏差。真正的逐帧精确要用**暂停 + 逐帧步进**（`next_frame` / `previous_frame` 动作已存在，`manual_seek` 已支持）。因此建议的精确流程是：**暂停 → 逐帧步进对齐 → "以当前位置为同步点"**，而不是反复加减偏移值。
2. **不同 fps 之间不存在"共同帧"。** 25fps 与 30fps 的素材只能做到时间对齐，做不到帧号对齐。UI 里"±1 帧"必须明确是**该视频自己的帧**。
3. **长录像会有时钟漂移。** 各机位晶振略有差异，录制数小时后固定偏移不再成立，需要**两点对齐**（同时解出偏移与速率偏差，用 `set_playback_rate` 补偿，范围 0.2–12 足够）。这应作为后续阶段，不应混进第一版。
4. **音频延迟是另一个正交旋钮。** 如果某机位的**音视频本身**不同步（不只是机位之间不同步），要用已有的 `Video.audio_delay_ms`（`set_audio_delay`），不是本功能的偏移。两者都要，别混淆。
5. **非等长素材的"同步播放"必然有一端先结束。** 对齐后较短的那路会先到片尾，此时应触发既有的 `VideoEndAction` 逻辑，而不是卡在越界提示上。

## 11. 分阶段实施

| 阶段 | 内容 | 依赖 | 状态 |
| --- | --- | --- | --- |
| **P1 核心** | `sync_offset_ms` 字段 + `SeekSyncMode.OFFSET` + 带偏移的 seek 镜像 + 越界钳制与格内提示 + 菜单动作（设点/微调/清除/只读显示） | 无 | **已实现** |
| ~~P2 持续校正~~ | 漂移检测与阈值重对齐 | P1 | **不做**（已定：暂停对齐好再播放） |
| **P3 对齐对话框** | 视频列表、当前定位、偏移、越界状态、Set / Align / 微调 / Reset | P1 | **已实现** |
| **P4 音频包络** | 独立分析 player + 按需片段解码 + 包络条绘制 | P1 | **已实现**；可视包络条见 §11 第六个修正 |
| **P5 自动对齐** | 互相关 + 置信度 + "一键对齐" | P4 | **已实现**（`Align By Sound`） |
| **P6 视觉胶片条** | 分析 player 抓帧 + 缩略图条 | P3 | **已否决**：实际素材三路画面无一致内容，见 §9 |
| ~~P7 两点对齐~~ | 解偏移 + 速率偏差 | — | 未开工（长录像才需要） |

P1 与 P3 已交付并通过测试。P2 按决定不做，因此**对齐是暂停时完成、播放时保持**：任何一次 seek 都会按偏移把其他视频带到同一时刻，但播放期间不再主动纠偏。这意味着长时间播放会有缓慢漂移，重新 seek 一次即可复位。

**P1 之后补上的一项（原设计漏了）**：播放/暂停状态原本不镜像，于是位置对齐了、一按播放又散开。现在在 OFFSET 模式下，任意一路的播放/暂停会作用于全体，且**开始播放前先按偏移重新对齐一次**——这样每次播放都从对齐状态起步，等于把"重新对齐"这个动作免费塞进了播放。它不需要 P2 的持续校正，因为只在用户意图发生时才动作，不会在播放中造成抖动。

### P4 / P5 的实现与设计的差异：取音频的方式换了

**设计里写的是 amem 回调**（`audio_set_callbacks`，边播边算包络），并因此担心"回调会顶替真实音频输出"，于是要求一个独立的静音分析 player。

**实际实现改成把片段转码成 WAV 文件再读**（`vlc_player/audio_probe.py`），三个好处：

| | amem 回调 | 转码成文件（实际采用） |
| --- | --- | --- |
| 与播放中的 player 的关系 | 必须在**另一个** player 上做，否则观众听不到声音 | 完全无关，谁都碰不到 |
| 耗时 | 音频时钟决定，≈ 片段的实时长度（6 秒片段等 6 秒） | 解码速度决定，实测远快于实时 |
| 复杂度 | 回调在 VLC 线程、共享内存、时间戳锚定、flush 重置 | 同步写文件、`wave` 读回来，无并发 |

所以音频输出的整个顾虑**消失了**——那个 player 从来没打算发声，只是把采样写进文件。转码用的 `--aout=dummy` 由 `libadummy_plugin.dll` 提供，Windows 打包脚本原先把音频输出裁到只剩 directsound，**已补上这一个**（否则发布版里按钮会没反应，而开发用的完整 VLC 里看不出问题）。

其余与设计一致：降采样到 **单声道 8kHz**（绕开 numpy 的前提，32 位 Windows 构建不能引入 numpy）、**50 块/秒**的 RMS 包络、纯 Python 互相关、用一个 `MIN_SCORE = 0.5` 的阈值拒绝"碰巧相似"。

与设计不同的一点：包络**没有画出来**。插值对齐的结果直接体现在 Offset 列和新增的 Sound 列（相关系数、以及哪一路是基准），可视包络条留作后续。

### 第二个修正：片段必须从头读，不能 seek

第一版实现用 `:start-time` 让 VLC 跳到目标位置附近再转码。**这是错的，而且错得很隐蔽**——实测在带音轨的 MP4（关键帧每 2 秒）上：

| 读取起始位置 | 片段实际起点误差 |
| --- | --- |
| 20000 | +399ms |
| 25000 | **−1112ms** |
| 18000 | −32ms |

推导（设 `a0`/`b0` 为两次片段**实际**起点，`e = 实际 − 请求`）：

```text
需要的修正量 = 测得的位移 + (e_B − e_A)
```

**旧代码只用了"测得的位移"，丢掉了 `e_B − e_A`。** 而视频容器的 seek 会落到最近的关键帧上，误差每个文件不同、随位置变化、**VLC 既不报告也无法补偿**（`get_time()` 在这种转码里取不到值，实测为空）。

危险的另一点：这些错误结果的**相关系数高达 1.000**——搜索找到的内容完全正确，错的只是"片段从哪儿开始"。任何置信度阈值都拦不住。

**修法：完全不 seek，从文件开头解码**，于是两次片段的起点都精确已知（= 0 + 窗口偏移），`e ≡ 0`。代价是解码位置之前的所有音频，但实测转码速度约 **300 倍实时**（40 秒音频 0.13 秒），所以一小时录像对齐到第 30 分钟约需 6 秒。

验证方式很直接：**同一段录音在两个位置各读一次，修正量必须是 0**（因为是自己对自己）。修改后测得 1ms / 0ms / 0ms，且与读取位置无关；修改前在同一批位置上偏差达 −1112ms。

**残留限制**：转码自身会给每次读取加上一个**编码相关的常量偏移**（实测 PCM 与 AAC 之间为 128ms）。同一批录像编码相同则抵消；**混用不同编码时会有约百毫秒级残差**，此时需要手动微调。

顺带一提，`WAV`（纯音频）的 seek 是精确的（误差 +1ms），**所以只用 WAV 做端到端测试会把这个问题整个掩盖掉**——最初的精度测试正是这么写的，测出 <1ms 就以为对了。现在唯一有意义的端到端测试用**音轨+视频**的 MP4。

### 第三个修正：比的是声音的形状，不是响度

真实素材上自动对齐**几乎没有生效**，Sound 列只有 **0.21 / 0.09**，全部低于阈值
0.5，因此被跳过（"Lined up 0/1/2" 每次不同，正是偶尔某个侥幸过线）。

原因不是阈值调错，而是**判据本身在这个场景下失效**：三台摄像机各自有自动增益，
一台离声源近、一台被挡住，它们的**音量曲线本来就不同**——而 RMS 包络几乎全是
音量信息。用"两台摄像机录同一事件、各自独立自动增益"实测对照：

| 判据 | 正确位移处的分数 | 后果 |
| --- | --- | --- |
| 原始响度包络 | **0.341** | 低于阈值，被跳过，视频根本没动 |
| 声音的形状（现在） | **0.667** | 采用 ✓ |

两种判据下**算出的位移都是精确的**（1500ms，误差 0）——差别只在"值不值得动手"。
现在先把每 0.5 秒的缓慢音量起伏减掉（`_shaped`，`SHAPE_SPAN_SEC = 0.5`），
比较剩下的形状；阈值随之降到 **0.3**（塑形后无关音频的分数接近 0）。
置信度也改为在**完整重叠段**上计算，不再用搜索计时所用的那一小段（4 秒）——
那 4 秒若恰好安静，对齐正确也会被打低分。

### 第四个修正：设完偏移必须再 seek 一次

偏移的语义是"这一路的时间轴上，某个共同时刻落在哪"，因此改偏移时
`VideoBlock` **刻意保留每个视频当前的共同时刻**（`p − o` 不变）。
后果是：**`Align By Sound` 把偏移算对了，但三个视频之间的实际错位一点没变**，
真正让视频走到一起的是下一次播放。

现在 `_measured()` 在设完偏移后立刻把所有人 seek 到基准那一路的时刻上
（`sync_offset_align_others`），按一下按钮就当场对齐，不再依赖之后的播放。

### 第五个修正：分数不能一个人说了算，基准也不能事先定死

P5 之后又改了三处，都在 [roadmap.md](roadmap.md) 的第 3~5 项里，
细节见 [audio-alignment.md](audio-alignment.md)：

| 改动 | 原来的样子 | 为什么 |
| --- | --- | --- |
| **分数之外再算"峰值突出程度"** | 只看相关系数是否过 0.5 / 0.3 | 绝对值对素材太敏感。改成"最佳峰值比次佳远处峰值高出多少"，低于 0.25 判为没把握、不动手（`Outcome.AMBIGUOUS`） |
| **测所有两两组合，基准由声音选** | 只跟第一路比 | 第一路可能是没音轨或内容差异大的那一路。现在基准是"被最多路认可的那一路"，并且三对答案要互相校验，对不上就报矛盾而不是挑一个 |
| **读过的那段声音留着** | 每次对齐都从头解码一遍 | 对齐就是"读—挪—再看—再读"，视频在两次之间会移动，而移动后的位置在已读过的那段里 |

一处实现上的要点：次佳峰值必须和最佳峰值**按同一分辨率**量。粗搜索是
20 块并 1 块，合并会把短促的声音摊平，于是"次佳离最佳多近"会随素材变化；
同一份合成素材上，用粗搜索的数算出 0.14，把候选按全分辨率重量得到 0.96。

### 第六个修正：包络条画的是已经读到的那段声音，不是又去读一遍

原设计的 P4 尾巴（§6.2 那一列、§7.4 的"按需片段 vs 实时滚动"）在这里收口：
**包络条不自己取数**，它画的就是 `Align By Sound` 刚读回来的那两条包络
（对话框留着，交给 `widgets/sync_strip.py`）。于是它是"读完之后的兜底"，
不引入第三条取数路径，也不需要 VLC 之外的东西。

横轴不是"某一路的时间轴"，而是**所有录像共用的那根时钟**：
`Sound(origin_ms, offset_ms)` 把一段读数放到 `origin − offset` 上
（这正是偏移的定义）。两个偏移一对，两段声音就落在同一处；微调把这一路
的声音沿时钟挪走，别的行不动——"看得见的微调"就是这么来的。
每路各自归一化到自己的峰值，因为要比的是形状不是电平（同 §11 第三个修正）。

滚轮缩放（以光标为中心）、左键拖动、双击回到两段共有的一段。
`utils/sync_audio.py` 里只多了一个 `Sound` 和 `MS_PER_BLOCK`，
纯算术，测试不需要播放器。

### 第七个修正：界面重做——一个基准、一根标尺、一次点击

第六个修正之后拿去用，问题是**看不懂**：每行都有 Align 和 Set 两个按钮，
分不清差在哪；包络条看不出画的是哪一段、是不是全部；每行各自缩放，几行的
刻度对不上；时间轴没有刻度也没有单位。这一版按"现在的功能"重排：

| 问题 | 现在的做法 |
| --- | --- |
| 每行两个按钮（Align / Set） | **Align 移到对话框底部，全dialog只有一个**，而且按钮上写着名字（`Align others to camera-2.mp4`）；`Set point` 留在行内，因为它是"登记这一路的数据"，本来就是一行动作 |
| 分不清对齐到谁 | 多了 **Align to 单选列**，全局只有一个：它决定底部按钮动谁、每行的灰色波形是谁、标尺的零点在哪。`Align By Sound` 读完把单选拨到声音选出的那一路 |
| 看不出画的是哪一段 | 每行的条子顶部画出**带刻度的标尺**（秒，相对零点），对话框里再给一句 `Showing 3.0 s of the 10.0 s that was read.`／`Showing all of it: 10.0 s.`，还有 `Fit` 按钮一键回到全部 |
| 几行的缩放不同步 | **窗口由对话框持有**：任一条子滚轮/拖动会说一声（`view_changed`），对话框把同一个窗口发给所有条子。标尺因此能连成一把尺子 |
| 不知道零点是什么 | 零点 = **基准那一路读到的声音的中点**。基准是"别人的尺子"，微调别人时它不动，所以"两条形状在零点处对上"就是调偏移的全部内容 |
| 不知道视频现在在哪 | 每行还有一条细线，画这一路此刻的共同时刻（`common_moment_ms`）；窗口被拖离当前时刻时看得出来 |

`Set point` / 微调 / `Reset` 的语义都没变，仍然**不移动画面**（`Set point`
只登记、微调只动被点的那一路）；底部那个 Align 是"以选中的那一路为准去动别人"，
等价于在那儿 seek 一次。

界面文字全部走 `translate("Dialog - Align Videos", …)`，**目前只有英文**：
`.ts` 由 Crowdin 管，到下一次翻译同步之前新界面不会有译文（见
[known-issues-and-risks.md](known-issues-and-risks.md)）。重做时顺手把一个更根本的
问题也修了：`pylupdate5` **只读"文本与上下文在同一行开头"的那种 `translate()`**，
而 `ruff format` 会把放不下的一律拆开、把文本挤到下一行——于是这类字符串
在任何语言里都永远是英文。对齐对话框这 18 处已按 `AGENTS.md` 里的写法修好
（独立成句 + 语句末行 `# fmt: skip`），`pylupdate5` 现在能看到该上下文的 **46 条**
字符串（此前 28 条）；包内其余 **82 处**同类问题已记入
[known-issues-and-risks.md](known-issues-and-risks.md)，由
`tests/test_translation_extraction.py` 卡住不许再增加。

### P3 的实现与设计的差异

| 设计里写的 | 实际实现的 | 原因 |
| --- | --- | --- |
| 表格里有"参考视频"单选列 | P3 时**没有**，到第七个修正才补上 | 存储语义不需要参考系（见 §2）；但**界面**需要一个，否则"对齐到谁"没处说 |
| 底部有"全部对齐到现在" | 先改成每行一个 **Align**，第七个修正又收回到底部一个 | 每行一个按钮看着灵活，实际让人分不清两个按钮的差别；"基准"是全局概念，操作也该是全局的 |
| 对话框是模态 | **非模态** | 打开期间必须能拖动进度条和逐帧步进，模态会让这个功能没法用 |
| 状态列只写"越界" | 越界 + 差多少时间多少帧，并区分"尚未开始/已结束" | 同格内提示 |

对话框的 `Set` / `Align` 都**不移动画面**：`Set` 只是登记当前位置，`Align` 是"以这一路为准去动别人"。微调（±1f/±1s）才会移动，且只动被点的那一路。

### P1 的实现与设计的差异

| 设计里写的 | 实际实现的 | 原因 |
| --- | --- | --- |
| 用 master 视频作参照算 `delta_i` | **无 master**：任何视频被 seek 时，`common = t_src − offset_src`，其他视频去 `offset_i + common` | 谁被 seek 谁就是参照，不需要额外状态，也不需要选参考视频 |
| 新增 `playlist/sync_offset_enforce`、`sync_offset_drift_frames` 等设置 | **没有新设置** | P2 不做，就没有需要调的东西 |
| `sync_offset_nudge_frames(±1)` | `sync_offset_shift_frames(±1)`，另有 `sync_offset_set(ms)` 承载 | 两个操作共用一套"保持当前时刻"的算法 |
| 偏移微调用 `manual_seek` 广播 | `sync_offset_set` 直接 `apply_sync_position`，不广播 | 偏移改变而公共时刻不变，其他视频本来就无需移动 |

一个实现上的要点：`manual_seek` 里 `self.time` 已被 `seek()` 同步设成目标值，所以新信号直接发 `self.time`，而不是像既有的 `sync_time` 那样用 `int(length * position)` 反算——后者会因浮点丢 1ms。

`tests/test_sync_offset.py`，P1 部分 46 个用例（其后 P3~P5 又加了一批，

1. **偏移的读写**（`sync_offset_txt` / `parse_sync_offset_txt`）：带符号的时间显示、fps 已知时的帧数、fps 未知时不显示帧数、各种输入写法（`1:15.000`、`+1:15.000`、`-0:05`、纯秒数）、非时间输入返回 `None`、以及"写出去再读回来"的往返。
2. **持久化**：`.gpls` 往返（正/负偏移）、未设置时 `sync_offset_ms` **不出现在文件里**、未设置读回为 `None`、没有该字段的旧播放列表读入为 `None`。
3. **偏移如何承载 seek**：用 `tests/test_close_teardown.py` 的"记录调用序列"范式，把真实的 `VideoBlocksManager.seek_sync_offset` 绑到一个只含它能读到的字段的 stub 上。覆盖用户给的原始例子（5s / 1:15 / 48s 三路互相对齐）、源视频自己不动、暂停状态被带到其他视频、偏移全未设置时退化为同一时刻、非 OFFSET 模式不动作、源视频已消失时不动作。
4. **表的一致性**（补上了 `known-issues-and-risks.md` 指出的缺口）：
   - `SECTIONS` 里每个 id 都是 `ACTIONS` 里真实存在的动作（递归遍历所有分段与子菜单）；
   - 每个子菜单名都在 `SUBMENUS` 里；
   - 每个动作都有 `func` 或 `menu_generator`。

   这三条把"`SECTIONS` 里写错一个 id → 右键时才 `KeyError`"这类问题变成构建期失败，这正是本功能新增 8 个动作后最需要的一道网。
5. **OFFSET 模式的接入**：枚举值、以及它出现在设置表单的 `_seek_sync_modes()` 里。

尚未覆盖（需要真实播放，属于 P3 之后）：`apply_sync_position` 里的越界钳制与提示文案（`_set_sync_out_of_range` / `clear_sync_out_of_range`）、以及在真实 VLC 上验证 seek 落点精度。

P4/P5 另需：包络数值正确性（合成正弦/冲击信号喂给纯函数）、互相关在已知偏移下能恢复出该偏移、弱相关时返回"不可靠"而非错值。

后来这些标记得太宽：纯算术、对话框、动作表那几组碰不到 libVLC，标着只是白扔覆盖率。现在只有真正 import 到播放器的那三组留标记，其余（含整个对齐对话框与"对齐如何拼装"那两组）在无 VLC 机器上照样跑。另见 [testing.md](testing.md) 的 "Tests that need VLC"。

## 14. 已决定的问题

1. **方向的措辞与符号** —— 决定：**不引入 `delta` 这个词**。菜单里用"Sync Point Forward / Back"（同步点前移/后移），描述的是**该视频自己时间轴上的位置**，客观且不会被读反；偏移值本身带符号显示（`+01:15.000`）。若日后加了 P3 的参考视频列，那一列才用"相对参考视频靠前/靠后"，因为有参照系才谈得上前后。
2. **旧的 PERCENT / TIMECODE** —— 决定：**原样保留在菜单里**。`SeekSyncMode` 现在是 Disabled / Percent / Timecode / Offset 四项，旧播放列表的值照旧可读，行为不变，也不加迁移。
3. **是否需要 P2 持续校正** —— 决定：**不做**。"暂停对齐好再播放即可"。因此没有新增任何与本功能相关的设置项（原设计的 `sync_offset_enforce`、`sync_offset_drift_frames` 都没有实现）。代价是长时间播放会缓慢漂移，重新 seek 一次即复位。
4. **素材有没有音轨** —— 决定：**有音轨**，因此 P4（音频包络）与 P5（互相关自动对齐）优先，P6（视觉胶片条）降级为无音轨素材时的后备。
5. **帧还是毫秒作主单位** —— 决定：**内部存毫秒，UI 同时显示帧数**。`sync_offset_ms` 是 `int`；`sync_offset_txt(offset, fps)` 在 fps 已知时附上帧数；`±1 帧` 按该视频自身 fps 换算（`sync_offset_shift_frames`），fps 未知时该动作灰显（`is_active_offset_in_frames`）。

### 仍未定、留给 P3 及以后

- 对齐对话框里是否需要一个"参考视频"列（只为显示"相对参考"的差值，不影响存储语义）。P5 之后基准由声音自动选，这一列仍未加。
- 互相关的置信度阈值，以及弱相关时的提示措辞。见 §11 第五个修正：现在有两个判据（`MIN_SCORE` 与 `MIN_PROMINENCE`），措辞落在对话框底部的说明里。
- 是否需要 P7 的两点对齐（偏移 + 速率），取决于素材时长是否长到晶振漂移可感。
- 包络的取数策略已定：按需片段（见 §7.4），读过的片段留着复用。
