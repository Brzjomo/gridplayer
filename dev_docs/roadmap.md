# 开发计划：同步偏移对齐

本文档记录同步偏移功能的**现状、已定决策和接下来的开发顺序**。
设计与原理见 [design-sync-offset.md](design-sync-offset.md)，
音频匹配子系统见 [audio-alignment.md](audio-alignment.md)。

## 二、已定决策（不要再翻）

| 决策 | 原因 |
| --- | --- |
| 内部存毫秒，UI 显示帧 | 帧率不可靠，毫秒是唯一稳定单位 |
| 旧 PERCENT / TIMECODE 模式**原样保留在菜单** | 明确要求，不删 |
| **不做**播放期持续漂移校正（P2） | "暂停时对齐好再播放即可"，用户明确决定 |
| **不做**画面/胶片条基准（P6） | **实际运用场景里三路画面几乎没有共通内容**，比对画面不成立 |
| 自动对齐**只对本机文件** | 流媒体每次读取都要重新拉取，而要对齐的是本地录像 |
| **不引入 numpy** | 32 位 Windows 构建拿不到 numpy 轮子，那个构建已经不带可选依赖 |
| 片段**从文件开头读，绝不 seek** | 视频容器 seek 落点误差可达 1 秒且无法补偿，见 audio-alignment.md |

由"画面基准不做"推出的一个结论：
**音频是唯一的自动对齐途径**。因此要么把音频这条路做到足够稳，
要么承认自动对齐在某些素材上不成立、老老实实退回手动。
两者都需要，但**优先级给了把音频做稳**——因为手动工具已经齐了
（Set Sync Point Here、±1f/±1s 微调、Align），而自动这条路还没有被验证过。

## 三、计划

### 1. 提交分支，并跑一次真实打包　【最高优先】

**为什么**：所有工作都在工作区里，一次误操作就没了。另外打包脚本里
`libadummy_plugin.dll`（音频探针要用的静音输出）**从未经过实际打包验证**——
这正是"开发环境看不出、发布版按钮没反应"的那类问题。

**做法**：请用户确认后提交；跑 `just build-win-package`，在打包版里
开对齐窗口、点一次 Align By Sound，确认不报错也不静默失败。

**验收**：打包版里 Align By Sound 能读出音频并算出结果（哪怕是"没把握"）。

### 2. 在真实素材上验证并定标　【用户参与】

**为什么**：目前唯一没验证的一环，也是 P5 能不能算"完成"的判据。
已知：三路真实素材在**旧判据（响度）**下只有 0.09 / 0.21，
现在改用声音形状后**尚未复测**。

**做法**：用户对三路素材点一次 Align By Sound，记录 Sound 列的三个数和
"Lined up N of M"。

**判据与后续分支**：

* Sound 列明显高于之前（比如 0.4~0.7）→ 音频这条路成立，继续第 3 项起。
* Sound 列仍在 0.2 附近 → 三路录音内容差异过大，**自动对齐在这套素材上不成立**。
  此时应：把 `MIN_SCORE` 的判定改成第 4 项（峰值突出度），
  若仍不行，就在 UI 上诚实说明"这套素材无法自动对齐"，并把重心移到手动工具打磨。

### 3. 缓存已解码的包络

**为什么**：现在每次对齐都要从文件开头解码到目标位置（约"位置 ÷ 300"秒，
一小时录像到第 30 分钟约 6 秒）。反复微调、反复对齐时这个代价被重复支付。

**做法**：按 `(路径, mtime, 大小, 窗口)` 缓存包络（内存 LRU，必要时落盘）。
对齐窗口存活期间复用；换素材才重读。

**验收**：同一素材连续两次 Align By Sound，第二次不再有任何解码等待
（日志或计时可见）。

### 4. 置信度改用"峰值突出程度"

**为什么**：这次的教训是**绝对相关系数对素材类型太敏感**——
同一份代码在合成素材上 1.000，在真实素材上 0.2。
"这个峰值比其它位置高出多少"是更接近"我有多确定"的量，且与素材无关。

**做法**：记录最佳峰值与次佳**远处**峰值的比，低于某个比值就判为"没把握"，
而不是只看绝对值。保留现有分数作为显示。

**验收**：合成素材（应判为有把握）与无关音频（应判为没把握）都能正确分类；
真实素材复测时判定结果与肉眼判断一致。

### 5. 多对互测，而不是只跟第一路比

**为什么**：现在基准是**列表里的第一路**，如果它恰好是"坏"的那一路
（没音轨、位置离得远、内容差异大），另外两路都会被带偏。
三路素材本来就该测三对。

**做法**：测所有两两组合，把各自推出的 δ 交叉校验；不一致时报告矛盾，
而不是挑一个用。基准改由用户选或自动挑最"合群"的那一路。

**验收**：三路中有一路无音轨时，另外两路仍能正确对齐，
并在界面上说明第三路为何没参与。

### 6. 对齐对话框里的包络条

**为什么**：原设计 P4 的尾巴。自动对齐不确定时，**让人眼比对两条包络**
是最可靠的兜底——这不是画面基准（那已否决），是声音的可视化。

**做法**：每行画一条包络条，基准行与当前行叠色显示，滚动/缩放对齐。

**验收**：肉眼能看出错位量级，并能据此手动微调到满意。

### 7. 两点对齐（偏移 + 速率）　【长录像才需要】

**为什么**：长时间录像两路之间会漂移，单点偏移修不了。
当前素材短，暂不需要。

**做法**：在录像上取两个远隔的时刻各测一次 δ，用斜率推出速率偏差。
这需要把偏移模型从"一个整数"扩展为"偏移 + 速率"，
**会影响 `.gpls` 格式和既有语义，属于破坏性改动**，动手前要单独评估。

### 8. 文档补齐

**为什么**：`dev_docs/` 已有音频子系统文档（`audio-alignment.md`），
但架构总览（`architecture.md`）和测试文档（`testing.md`）还没有指向它。

**做法**：在 `architecture.md` 的模块表里加入
`utils/sync_audio.py`、`utils/sync_align.py`、`vlc_player/audio_probe.py`；
在 `testing.md` 里补一节"需要 VLC 的测试"（`needs_vlc` 标记与临时 wav 的用法）。

## 四、不建议现在做的

| 想法 | 为什么不做 |
| --- | --- |
| 用 FFT / 频谱指纹提高区分度 | 没有 numpy，纯 Python 的 FFT 太慢；8kHz 包络已能到毫秒级 |
| 在播放中实时校正 | P2 已决定不做，且会造成播放抖动 |
| 支持流媒体的自动对齐 | 每次读取都要重新拉取，代价与可靠性都不成立 |
| 把音频抽出整段落盘再比对 | 一次解码整部录像，比现在按需读到目标位置更慢 |

## 五、已知的量化限制（要在 UI 上诚实说明）

* **混用不同编码来源**时约有百毫秒级残差：转码自身带有编码相关的常量偏移，
  实测 PCM 与 AAC 之间为 128 ms。同一批设备同编码则抵消。
* **可对齐范围 ±12 秒**：更远的错位需要先手动拉近。
* **纯静音或与基准毫无相似之处的录像**会被跳过（这是有意的，不是 bug）。
* 读取耗时与"位置在录像中有多深"成正比，见第 3 项。
