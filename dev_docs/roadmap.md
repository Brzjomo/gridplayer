## 二、已定决策（不要再翻）

| 决策 | 原因 |
| --- | --- |
| 内部存毫秒，UI 显示帧 | 帧率不可靠，毫秒是唯一稳定单位 |
| 旧 PERCENT / TIMECODE 模式**原样保留在菜单** | 明确要求，不删 |
| **不做**播放期持续漂移校正（P2） | "暂停时对齐好再播放即可"，用户明确决定 |
| **不做**画面/胶片条基准（P6） | **实际运用场景里三路画面几乎没有共通内容**，比对画面不成立 |
| 自动对齐**只对本机文件** | 流媒体每次读取都要重新拉取，而要对齐的是本地录像 |
| **不引入 numpy** | 32 位 Windows 构建拿不到 numpy 轮子，那个构建已经不带可选依赖 |
| 片段**从文件开头读，绝不 seek** | 视频容器 seek 落点误差可达 1 秒且无法补偿，见 audio-alignment.md |

由"画面基准不做"推出的一个结论：
**音频是唯一的自动对齐途径**。因此要么把音频这条路做到足够稳，
要么承认自动对齐在某些素材上不成立、老老实实退回手动。
两者都需要，但**优先级给了把音频做稳**——因为手动工具已经齐了
（Set Sync Point Here、±1f/±1s 微调、Align），而自动这条路还没有被验证过。

## 三、计划

### 1. 打包，并在打包版里验证 Align By Sound　【已完成】

**为什么**：打包脚本里 `libadummy_plugin.dll`（音频探针要用的静音输出）
**从未经过实际打包验证**——这正是"开发环境看不出、发布版按钮没反应"的那类问题。

**做法与结果**：本机跑了一次完整打包（VLC 3.0.24 win64 + PyInstaller 6.22.3 +
内嵌 libVLC），产出 `dist/GridPlayer-0.5.5-win64-portable.zip`。
过程里抓到**两个真问题，都在发布版里表现为"功能悄悄不工作"**：

1. **打包脚本少了三个插件目录**。读完一段声音靠的是把片段转码成 wav
   （`#transcode` → `#std{access=file,mux=wav}`），而 `build_win.sh`
   从不复制 `stream_out`、`mux`、`access_output`——它们都不是放视频需要的。
   实测：按脚本原样做出来的 libVLC，探针**一个字节都读不出来**；
   少任何一个目录都一样。（`libadummy_plugin.dll` 之前补对了，
   但那条链的另外三节没有。）
2. **空的 `plugins.dat` 比没有更糟**。给空目录生成的缓存是 **24 字节**，
   应用看到它就加 `--no-plugins-scan`，于是 VLC 一个插件也不加载、
   `libvlc_new` 返回空——**每个解码进程都起不来，整个播放器放不了任何视频**，
   而界面看上去一切正常。实测就是这样：打包版启动正常、日志里只有
   "VLC failed to initialize"。

两处都已修：脚本补上三个目录（`scripts/pyinstaller/build_win.sh`），
应用只把**像样的**缓存当缓存（`MIN_PLUGIN_CACHE_BYTES`，
`vlc_player/instance.py`），并各加了测试盯住。

**验收**：打包版里读出音频并算出结果——探针的端到端用例就是拿**最终
libVLC 载荷**跑的（6 项全过）；打包版自身启动、载入媒体、播放均无错。
对话框里那一下点击仍要用户自己按（对齐本身要靠真实素材，见第 2 项）。

**还没做的**：`just build-win-package` 里的 **Inno Setup 安装包**那一步
（本机没装 Inno Setup，只出了便携版 zip）；以及官方脚本原本从
videolan.org 下载 VLC，本机网络到不了那里，是从清华镜像下载并
**核对三家镜像的 SHA256 一致**（`fcf3085…6323`）后使用的。

### 2. 在真实素材上验证并定标　【用户参与】

**为什么**：目前唯一没验证的一环，也是 P5 能不能算"完成"的判据。
已知：三路真实素材在**旧判据（响度）**下只有 0.09 / 0.21，
现在改用声音形状后**尚未复测**。

**做法**：用户对三路素材点一次 Align By Sound，记录 Sound 列的三个数和
"Lined up N of M"，以及底部说明里"没被移动的那几路为什么没被移动"。

**判据与后续分支**：

* Sound 列明显高于之前（比如 0.4~0.7）→ 音频这条路成立，继续第 6 项起。
* Sound 列仍在 0.2 附近 → 三路录音内容差异过大，**自动对齐在这套素材上不成立**。
  第 4 项（峰值突出度）已经做完，所以此时应该：在 UI 上诚实说明
  "这套素材无法自动对齐"（现在的说明已经会给出每路各自的原因），
  并把重心移到手动工具打磨（第 6 项包络条）。

### 3. 缓存已解码的包络　【已完成】

**为什么**：每次对齐都要从文件开头解码到目标位置（约"位置 ÷ 300"秒，
一小时录像到第 30 分钟约 6 秒）。反复微调、反复对齐时这个代价被重复支付。

**做法（与计划的差异）**：没有缓存"包络"本身，缓存的是**那一段声音**
（转码出来的 wav）。原因是包络按需从 wav 里读出来只要毫秒，而把整段包络
留在内存里要为每路录像占几十 MB（一小时录像读到位居第 30 分钟，包络
90 万个浮点）；wav 在盘上只有 16 KB/秒。

`SnippetCache`（`utils/sync_audio.py`）按 `(路径, mtime, 大小)` 记住一路录像
**从文件开头到读到过的最深处**，任何更浅的请求都从中切出来；键变了
（文件被改写）就重读。最多留 3 路，淘汰时删文件，进程退出时删临时目录。
探针（`audio_probe.py`）只负责写，缓存由 `AudioProbe` 共用一份。

**验收**：`tests/test_sync_audio.py` 里缓存那一组（无 VLC 机器上可跑）
证明同一段不重读、更浅的窗口由更深的那次覆盖、文件变了要重读、超出录像
结尾的请求不重复读；`needs_vlc` 的
`test_a_recording_read_once_is_not_decoded_again` 在真实探针上盯住"第二次
不调用 `_write_snippet`"。

### 4. 置信度改用"峰值突出程度"　【已完成】

**为什么**：这次的教训是**绝对相关系数对素材类型太敏感**——
同一份代码在合成素材上 1.000，在真实素材上 0.2。

**做法**：`best_lag()` 除分数外返回 `prominence` = `1 − 次佳远处峰值 / 最佳峰值`，
"远处"取 1 秒以外（`PEAK_SEPARATION_SEC`），低于 `MIN_PROMINENCE = 0.25`
即判为没把握（`Outcome.AMBIGUOUS`），不动那段视频。分数照旧显示。

一个实现要点：**次佳峰值要和最佳峰值用同一把尺子量**。粗搜索是合并过的
（20 块并 1），合并会把短促的声音摊平成近似一个值，于是"次佳离最佳多近"
会随素材变化——同一份合成素材上，用粗搜索的数算出来是 0.14，把候选
重新按全分辨率量一遍是 0.96。所以粗搜索给出候选（最多 8 个，排除答案
附近 1 秒内），它们和答案一起按全分辨率重新算分。

**验收**：`TestHowSureTheAnswerIs` 覆盖"值得匹配的形状判为有把握"、
"周期性的声音（一秒的片段重复 12 次）判为没把握"、"无关的录音分数低于
阈值"。真实素材复测仍待第 2 项。

### 5. 多对互测，而不是只跟第一路比　【已完成】

**为什么**：原来基准是**列表里的第一路**，如果它恰好是"坏"的那一路
（没音轨、位置离得远、内容差异大），另外两路都会被带偏。

**做法**：`align()` 测**所有两两组合**。基准改由声音选——**被最多路认可的
那一路**（并列时取总分高的，再并列取靠前的）；三路时通常是中间那一路。
每路的位移沿"连接它和基准的最少几对"推出。然后**交叉校验**：
对任意一对 (i, j)，`δ_ij` 应当等于 `δ_i − δ_j`（都相对基准），
残差超过 `CONFLICT_MS = 300 ms` 就判为矛盾——把涉及矛盾的那几对剔掉，
只靠这些对才能定位的视频一律不动，界面上报出矛盾了多少毫秒。
300 ms 的选择：高于混用编码带来的约 128 ms 常量，远低于挑错峰值的秒级误差。

界面上，"没被移动"的每一路都带上原因（没读出声音 / 和谁都对不上 /
匹配的位置太多 / 声音自相矛盾 / 和基准没有通路），Sound 列在旁边标
`weak` / `unsure` / `conflict` / `unlinked`。

**验收**：`TestSeveralReadingsAtOnce`（把"每对算出多少"直接喂进去，
不需要播放器）覆盖基准选择、矛盾报告且不动手、矛盾之外照常对齐、
无音轨那一路不影响另外两路；对话框层面
`test_one_file_with_no_sound_does_not_stop_the_other_two` 盯住界面文案。

顺带修掉一个被这批测试逼出来的错误：负延迟时重叠长度原来按 `other` 的长度
算，两段读数等长时看不出来，**一长一短时整对就丢了**
（录像在自己那段片段结束时会给出更短的读数）。现在按参照那段的长度算，
`TestReadingsOfDifferentLengths` 盯住它。

### 6. 对齐对话框里的包络条　【已完成】

**为什么**：原设计 P4 的尾巴。自动对齐不确定时，**让人眼比对两条包络**
是最可靠的兜底——这不是画面基准（那已否决），是声音的可视化。

**做法（与计划的差异）**：**不额外解码**。包络条画的就是上一次读数留下的
那两条包络（`AlignVideosDialog._readings` 交给 `widgets/sync_strip.py`），
所以它是"读完之后的兜底"，不是另一种取数方式。每行一条，横跨整行、
在按钮那一行的下面，行宽多少就画多少。

横轴是**所有录像共用的那根时钟**（`Sound`：`origin − offset`），
于是两段声音的偏移一对上就落在同一处，而微调会把这一路的声音沿时钟挪走、
别的行不动——这就是"看得见的微调"。配色取自调色板（基准一种、本行一种，
叠着画），并且**每路各自归一化到自己的峰值**：两台机器的录音电平本来
就不同，要比的是形状。

滚轮缩放（以光标处为中心）、左键拖动平移、双击回到"两段声音共有的那一段"。

**验收**：`TestPlacingTheSoundOnTheClock`（不需要 VLC）盯住时钟换算、
按列取峰值、共有段的边界；`TestTheSoundStrips` 盯住"读数进来后两条声音
被交给条子""偏移一改，这一路的声音沿时钟移动""没变化就不重画"
"真的画得出来（离屏 `grab()`）""滚轮与拖动"。
肉眼那一关要真人看，那本来就是它的用途。

### 6b. 界面重做：一个基准、一根标尺　【已完成】

**为什么**：第六项交付后实际用起来"看不懂"——每行都有 `Align` 和 `Set`
两个按钮，分不清差在哪；包络条看不出画的是哪一段、是不是全部范围；几行的
缩放各自为政，刻度对不上；时间轴没有刻度也没有单位；而且整个对话框只有英文。
详见 [design-sync-offset.md](design-sync-offset.md) §11 第七个修正。

**做法**：

* **`Align` 从每行收到底部，全dialog只有一个**，按钮上写着它动谁
  （`Align others to camera-2.mp4`）；`Set point` 留在行内——它是"登记这一路的
  数据"，本来就是一行的动作。两者用词也分开了：`Sync point`（列）/ `Set point`（按钮）。
* **`Align to` 单选列**：全局只有一个基准，决定底部按钮动谁、每行灰色波形是谁、
  标尺零点在哪。`Align By Sound` 读完把单选拨到声音选出的那一路；判定用的
  基准（`_run_reference_id`）与"要对齐到谁"（`_align_to`）是两个状态，都留着。
* **标尺画出并且共享**：每条子顶部画带刻度和秒标签的标尺带；**窗口由对话框持有**，
  任一条子滚轮/拖动通过 `view_changed` 上报、对话框发给所有条子，于是几行的
  刻度连成一把尺子。另有一句人话说明范围：`Showing 3.0 s of the 10.0 s that was read.`
  / `Showing all of it: 10.0 s.`，以及 `Fit` 按钮。
* **零点 = 基准那一路读到的声音的中点**（`Sound.read_around_ms`）：微调别人时它不动，
  "两条形状在零点处对上"就是调偏移的全部内容；每行另有一条细线画这一路此刻的
  共同时刻（`common_moment_ms`）。
* 列名从 `Holds nothing` 改成 `Range`，`Offset` 改成 `Sync point`，`Sound` 改成
  `Sound match`。

**验收**：`tests/test_sync_offset.py` 202 项全过（含新增的：唯一基准、
按钮名字跟着基准走、逐行开关不误触发、所有条子同一窗口、滚轮以光标为中心、
拖动同步、标尺步长/刻度/标签的纯函数）。离屏渲染看过布局。

**没做完的一件**：界面只有英文。`.ts` 由 Crowdin 管、此处不许改，
所以到下一次翻译同步之前，这个对话框（以及新增的其它字符串）在所有语言里都是英文——
已记进 [known-issues-and-risks.md](known-issues-and-risks.md)，新字符串清单在本轮汇报里。

### 7. 两点对齐（偏移 + 速率）　【长录像才需要】

**为什么**：长时间录像两路之间会漂移，单点偏移修不了。
当前素材短，暂不需要。

**做法**：在录像上取两个远隔的时刻各测一次 δ，用斜率推出速率偏差。
这需要把偏移模型从"一个整数"扩展为"偏移 + 速率"，
**会影响 `.gpls` 格式和既有语义，属于破坏性改动**，动手前要单独评估。

## 四、不建议现在做的

| 想法 | 为什么不做 |
| --- | --- |
| 用 FFT / 频谱指纹提高区分度 | 没有 numpy，纯 Python 的 FFT 太慢；8kHz 包络已能到毫秒级 |
| 在播放中实时校正 | P2 已决定不做，且会造成播放抖动 |
| 支持流媒体的自动对齐 | 每次读取都要重新拉取，代价与可靠性都不成立 |
| 把音频抽出整段落盘再比对 | 一次解码整部录像，比现在按需读到目标位置更慢 |

## 五、已知的量化限制（要在 UI 上诚实说明）

* **混用不同编码来源**时约有百毫秒级残差：转码自身带有编码相关的常量偏移，
  实测 PCM 与 AAC 之间为 128 ms。同一批设备同编码则抵消。
* **可对齐范围 ±12 秒**：更远的错位需要先手动拉近。
* **纯静音或与基准毫无相似之处的录像**会被跳过（这是有意的，不是 bug）。
* 读取耗时与"位置在录像中有多深"成正比，见第 3 项。
